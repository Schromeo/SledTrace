## 0. 只读这一页，也能掌握方向

定位：**本地 AI 工作流调试与改进验证工具：定位任务在哪一层失败、证据缺在哪里，再帮助开发者判断修改是否真的有效。** 用量与成本服务于这个闭环，不以报警数量或 token 图表作为核心价值。

保留 RAG、Python SDK、Go/SQLite/React 和现有 retrieval/llm/tool 记录。Python 仍是主要接入路径；MAMR 是一个有明确边界的 TypeScript 应用取证试点，不代表通用 JavaScript SDK、多 Agent runtime 或分布式追踪。

主线：源头采集 → 失败定位 → 最小前后比较 → 一次真实修复/回退决定 → 按证据增加提示 → 独立使用 → 可靠性冻结。

三条底线：未知不写零；重复不写浪费；更便宜不写更好。一次片只追一个可展示结果，写定验收后停止。

本轮不重新验证历史发布或远端 PR 状态。保留候选提交及证据，整合候选栈是单独的审阅工作，不重写公共 main。

## 2. 优势、竞争力与验证标准

我们的可用资产是本地链路、轻量显式埋点、RAG 证据、已知/未知数据语义和可见验收习惯。它们不是已证明的市场壁垒。

要验证的差异化是：**比散落的日志更快回答“哪里坏了、为什么只能判断到这里、改哪一处、改后是否更好”。** 不追赶所有可视化、框架和价格库。

- 用户友好：先给失败层级与下一项可检查证据，再展开调用详情；把未知、未评估、错误分开。
- 本地与隐私：最少字段、源头脱敏、无自动上传；本地文件也可能敏感。
- 框架薄边界：先验证一个应用专用映射，而不是所有 Agent 框架通吃。
- RAG 复用：共同复用采集、计量、事件关联、结果比较；检索相关规则只覆盖真正检索步骤。
- 真实积累：可脱敏的问题样本、反例、契约和修复对比，比报警规则数量重要。

内部 dogfooding 可以证明技术/开发帮助，不能代替独立用户采用。连续两个合适场景仍无可行动收益，就缩小产品承诺，不用加适配器掩盖需求问题。

## 3. 用户与 1.0 边界

首要用户：能够修改应用的独立开发者/小团队，维护短时、可结束、可重复验证的 AI 工作流。Python 是主要 SDK 路径；MAMR 的单应用诊断 bundle 是受限的跨语言取证路线，不扩张为所有语言支持。

1.0 目标能力：

- 观察显式接入并提交的调用、工具与任务结果，保留未采集/不完整状态。
- 根据应用提供的合同校验和执行证据定位失败；不把相关顺序当成因果证明。
- 展示计量来源、覆盖缺口、时间与参考费用；失败尝试保留在账本和比较中。
- 同任务、固定验收的修改前后比较，帮助保留或撤销修改。
- D1 必须可用；D2/D3 只在证据达标时发布，**没有两条或三条告警的配额**。
- 支持范围内无源码启动、基本记录查找、隐私控制、兼容与可靠性。

不承诺：自动执行/修复 Agent、私有思维链、实时预算强制中止、进程崩溃零丢失、
通用框架适配、精确账单、分布式图编辑器、任意工具重放、云/认证或内置通用语义裁判。

若用户实际需要实时控制系统，重新选型，而不是悄悄塞进这个版本。

## 4. 衡量价值，不衡量忙碌

北极星：开发者完成一次“发现问题 → 修改 → 验证 → 保留/撤销”的闭环。

| 指标 | 记录办法 | 决策用途 |
| --- | --- | --- |
| 接入成本 | 安装/埋点/配置/求助各自用时 | 首条自己的 trace 目标约 10 分钟，前置设置另计 |
| 定位成本 | 打开记录到指出具体失败层与下一步检查 | 初步目标 5 分钟，非已达 SLO |
| 数据可信 | 源字段、持久化值、UI 逐项核对 | 缺失不补零，来源与完整性各自显示 |
| 修改价值 | 固定输入/验收、保留全部结果与额外尝试 | 不只挑成功或便宜的一次 |
| 独立重复使用 | 两位非开发参与者另一天自行再次使用 | 1.0 产品门槛，不用内部代操作充数 |

质量不降且成本/耗时改善是一种价值；避免错误修复或识别回归也是价值，但不能宣传为节省。少量样本支持具体决策，不支持普遍准确率或市场结论。

## 5. 深层 Trace、语义与纠错的契约

### 5.1 四层证据，不收集模型私有思维链

| 层 | 最小证据目标 | 边界 |
| --- | --- | --- |
| 调用 | run/attempt 标识、provider/model、配置版本、开始/结束或未知、usage 与来源、finish reason | 不从 UI 数字伪造原始 provider 返回 |
| 应用校验 | validator/version、阶段、稳定 reason code、字段路径、预期类型/实际结构 | 默认不留原文、私密参数或任意错误文本 |
| 流程 | phase、显式前驱/恢复引用、状态版本、终止/恢复可用性 | parent 表示包含，不自动表示原因；时间相邻也不证明依赖 |
| 任务 | 产物是否存在、流程结果、质量评估及标准版本/来源 | interrupted、contract failure、quality not evaluated、human rejected 分开 |

这是待定稿的语义需求，**不是已存在或批准上线的新 schema**。P2/P3 先检查现有字段，公共/持久化契约另过决策门槛。标识稳定、跨 run 不串联；没有证据就显示未知。
MAMR posthoc trace 的 accepted=false 是历史映射局限，不得静默改写数据库使旧图看起来正确。

### 5.2 用量、金额与时间

- 直接 provider、框架转述、应用报告、手工映射、fixture、估算分别标注。已知来源不代表账单已核对；来源未知也不必否定所有数值。
- 保存 input/output/total/cache/reasoning 的包含关系与冲突；缺分项不反推。已观察调用覆盖与整个应用的未观察覆盖分开。
- 失败 usage 已知就计入，未知不算免费；去重后再聚合，父汇总不与子调用双算。
- 成本带币种、模型匹配、价格来源/快照/计费类别；无法匹配则未知。应用 UI 默认费率只作应用估算，不当官方模型账单。
- 旧 trace 不自动用新价格覆盖；不同币种/口径不混比。工具费用和本地资源费用未接入则注明。
- 原始时刻、reported duration、导入时刻分开；并行时长相加不等于墙钟时间。事后映射 runtime 不是原会议耗时。

### 5.3 诊断政策：最多三族，D1 必做，其余有条件

| 族 | 判定与证据 | 排除 / 弃权 | v0.8 要求 |
| --- | --- | --- | --- |
| D1 失败定位及影响链 | 应用显式校验错误/调用失败、相关 attempt、明确依赖和阻断结果 | 缺字段只定位到已知层；不猜模型内部原因，不把所有后续失败重复报为根因 | 必做 |
| D2 相同失败无可见条件变化地重复 | 显式恢复链、稳定错误类别、安全参数可比性和相关状态证据 | 退避、暂时限流、改参数、状态变化；状态不可见不下重复浪费结论 | 条件性 |
| D3 违反声明的执行约束 | 应用明确提供的调用/token/时间/费用或停止策略，及可比完整计量 | 不编默认阈值；缺计量不能说未超限；估算越界不是账单越界 | 条件性 |

D1 的已知错误是事实展示，其“原因解释”仍受证据限制；D2 是保守建议；D3 是事后检查，不是运行中熔断。源头同一次失败引发的下游症状应合并为一个问题及影响列表，而非堆警告。

重复相同工具结果暂为观察信息；PydanticAI 动态指令重复正是反例。RAG 七类规则继续限定检索覆盖。数据缺失/覆盖 badge 不与错误或浪费混为一谈；0 warnings 不表示健康。

每条可选规则进入前写明必要字段、判定、反例、未知降级、开关与行动建议。启发式才需事先留出的正反/边界集（初始约 8–12 个为设计参考，报告实际数量，不是全项目门槛）；确定性 validator 用分支测试，不能等待 12 次真实失败才开发。

### 5.4 语义判断与纠错

先接收应用确定性评估、人工评审或已有外部评估结果，记录标准版本、来源、未评估状态；不自称判断所有答案正确与否，不以内置 LLM-as-judge 作为 1.0 前提。

纠错顺序：展示已知失败层和字段 → 给出可核查检查方向 → 开发者选择单一干预 → 应用负责有限修复/恢复 → 记录额外尝试与结果 → 比较保留/撤销。SledTrace 不自动换模型、放松 validator、重放有副作用工具或偷偷补发请求。

## 7. 固定试验场与证据分类

只保留三个互补对象：

1. MAMR：真实多 LLM 工作流、格式合同、暂停/恢复、任务产物；当前是内部 dogfooding，未观察工具执行。
2. PydanticAI：已固定公共参考的实际工具与正常重复反例；区分 TestModel、历史真实模型 probe、新模式 stub。
3. 现有 RAG：检索及旧记录兼容回归，不扩成新框架筛选。

证据分别标注 fixture、公开参考离线运行、真实模型调用、内部实际开发帮助、外部独立重复使用。真实模型成功不自动比确定性失败分支覆盖更适合证明 validator；外部采用与执行真实性是不同维度。

本次四调用中断没有保留足够原始证据，不能靠推测或无限复现恢复历史根因。之后一次成功运行也可验证采集链，失败分支用脱敏 fixture；不追着随机错误跑。

## 8. M2.5：P1–P3 可追溯采集

共同验收：一个成功与一个失败路径从源事件到存储再到 UI 可核对；其中 fixture 与 live 明确区分，旧记录可读。下面工期是有效开发时间估计，不包含授权/外部等待。

### P1 — 精确校验原因（0.5–1.5 日）

- 用户结果：错误不再只有 “statement or card invalid”，能区分缺失、类型、空值、长度或具体结构失败。
- 所属仓库：MAMR。先读它自己的 AGENTS/任务和校正工作流，检查其他任务/脏改动；SledTrace 规划不覆盖另一仓库契约。
- 只增加稳定原因码、字段路径与安全结构摘要，保持现有接受/拒绝语义；消息兼容，避免把任意模型值当字段名直接泄露。
- 在现有失败事件/记录边界保留诊断，验证 UI 能读到；跨公开事件契约变化先明示门槛。
- 离线测试：缺失/类型/空白/长度边界、合法旧对象、错误嵌套结构、假秘密不进入诊断；原判定不变。
- 不做 prompt/model 更换、自动 retry、放松校验、SDK 重写、付费调用。
- 交付：一份可读错误样例与测试证据；达到字段定位就停，不顺手修模型行为。

### P2 — 捕获真实尝试证据

- 在应用原有模型调用与校验边界记录实际 run/attempt、phase、provider/model、usage 来源、终止信息、计时和安全配置版本。
- 区分调用终止、合同校验、流程结果、任务质量；失败已有 usage 不丢，缺失明确。
- 恢复引用只由应用显式提供；不推断未发生的工具/因果关系。
- 源头脱敏、内容采集默认最小化，秘密 fixture 覆盖事件/存储/日志。
- stub/离线事件测试先过；任何 live 另定预算/次数。可成功也可失败，均验证保真。
- 不建通用 JS SDK、全部流式 delta 存储或 Collector live 协议；采集实时发生，交付可等结束/暂停。

### P3 — 受限脱敏 bundle 导出/导入（2–3 日，必要存储前置另拆）

- 应用 opt-in 导出版本化非执行 JSON，SledTrace 薄导入器保留原时刻和 provenance；未知不由导入过程补造。
- 这是已选 MAMR 试点，不是任意第三方 trace 格式平台。默认只允许声明字段，限制文件大小/数量/版本，不执行内容。
- 先实现 R1 必要原子保存与明确重复语义：同 ID 同数据不重复计量，不同数据报冲突；不靠重新生成 ID 掩盖重导。
- 若该前置无法在 3 日内安全完成，单列 P3a 存储片再做 P3b 导入，WIP 仍为 1；不跳过安全或假称幂等。
- 验收：成功/中断 fixture round-trip、重复/冲突/事务失败/非法版本、秘密不外泄、旧 RAG 读取；实际 Dashboard 显示来源/时间/状态。
- 到 P3 重新估算一次；仍不能解释一个具体字段失败就缩小映射，不加第二个应用适配器。

## 9. M3：P4–P7 诊断、比较与真实修改

### P4 — D1 失败层级与影响展示（1–2 日）

复用现有详情/步骤 UI，首屏回答哪一步、哪一层、何种已知校验失败、阻断了什么、哪些证据仍缺失。区分 provider failure、contract failure、workflow interrupted、quality not evaluated。显式关联才展示影响链；无关联只列事实。
验收包含源错误/下游症状折叠、旧记录降级、未知字段、键盘可操作，以及成功/失败真实页面截图。不造通用 DAG，不加启发式“根因分数”。

### P5 — 最小结果约束比较（2–3 日；承接 E5）

开发者自行运行两个版本；按 case/input/config/验收版本关联，展示结果、失败、调用、已知 token/费用/墙钟时间及缺口。单项变化不够控制混杂时注明。
相同未知、基线零、币种/口径不同不给伪百分比。保留失败、取消和导入缺失在分母，旧 warning 减少不等于质量上升。先双 run 页面和简单摘要，不建调度平台。
测试同任务可比/不同任务不可比、缺项、失败更便宜、真实零、不同价格口径，真实页面可追原证据。

### P6 — 一次证据驱动的 MAMR 修复（1–2 日，不含付费等待）

P6 的固定出口不随预审/展示/采集/读取子片拆分而后移。
上述必要前置计入同一个 P6 的有效投入；不能换片号重置 1–2 日估计。
此前累计工时未知，不从日期或片数推算。已知投入与未知历史段分别记录在
CURRENT_TASK；接近原估计两倍先重新决策，不静默加时。

最小证据优先：先比较获准提供的脱敏既有错误与有限复现是否足够，
再决定是否需要扩展源头采集。原因码证明失败类别，不自动证明根因。
既有 [P6C 采集提案](P6_REDUCTION_CAPTURE_PROPOSAL.md) 保留为待专项批准的
候选，不是默认下一片。若旧案例无法重建，明确归档其缺口，不追随机失败；
新受控任务/应用修改/付费实验仍需要各自授权。
实验结论允许保留、撤销或证据不足；证据不足不关闭 M3b。
当前实现/控制/根因状态只由 CURRENT_TASK 与 AI_HANDOFF 维护。

先用新证据确认原因，再挑一个改动（例如输出合同对齐或有界恢复；不是预先决定放松校验）。记录 baseline、应用版本、标准、输入和尝试。
先一对运行验证可行性；有价值再用 3 个固定任务 × 每版本 3 次作小样本决策。用户费用不足可减样本并降低结论，不能擅自扩预算。
最多两轮有新证据的修复；不收敛就交证据报告/收窄，不凑成功截图。应用自己控制恢复和副作用，SledTrace 记录额外成本与结果。
M3b 门槛：至少一次真实问题定位引导修改，使用者能解释保留/撤销；可以是有效修复或有用回归发现。仅离线测例通过不满足此门槛，内部收益不冒充外部采用。

### P7 — D2 或 D3（可选，单片 1–2 日）

只有真实诊断问题需要时选择一族，不同时做两族。沿第 5 节定义前提/反例/弃权，先留出测试，再实现。没有可行动收益就不上线，不阻塞 P5、runtime 或独立试用。
相同工具返回仅作观察，不成为 v0.8/1.0 固定交付指标。

v0.8 候选门槛：M2.5、D1、最小比较、一次真实开发决定、RAG/旧记录/隐私/必要存储验证及确切候选发布验收。没有诊断条数配额，也没有无条件节省承诺；版本发布仍另获授权。

## 10. M4：v0.9 — 让别人不用我们陪着也能使用

### U1 — 去掉完整产品对源码仓库的依赖

先做最多 1–2 日可行性调查，随后一次 2–3 日的最小实现片。首选复用现有 Go Collector + 内嵌构建后的静态 Dashboard；这是待验证的分发方案，不是已交付架构。

- 比较预编译独立 runtime、平台 wheel/可选安装包的维护成本；只选一种主路径。
- 理想用户结果：安装 SDK；明确安装/取得本地 runtime；一个命令启动并获得可点击地址。不要求用户安装 Go、Node 或克隆源码。
- 不把“必须恰好只有一个 pip 命令”当作架构约束；SDK 轻量可单独使用，完整产品可以有清楚的第二步。
- 如果需要下载可执行文件，用户必须知情，绑定可信发布来源、版本和 checksum；不默默下载 latest 并执行。首次下载与之后离线启动分开测试。
- 先定一个有 CI 和实际试用设备的平台组合；增加第二个平台需有测试资源。Windows 是当前用户环境，但现有 SQLite 驱动的可构建性必须先核对。
- 显示 runtime/SDK 版本、服务地址、数据库位置；启动失败可操作，退出只清理由自己创建的进程。
- 默认 loopback，不打开局域网服务；适配静态 UI 的 API 路由，不为一个页面保留不必要的双服务端口。
- 测试：全新环境、仓库外安装、启动、关闭、再次启动、已占端口、离线已安装启动、不支持平台提示、数据保留。

退出条件：一条无需源码的支持路径可重复。超过调查预算就提交方案/阻碍，选择手动安装独立 runtime 或收窄平台；不重写 Python backend，不拖着不决。该能力仍是完整产品 1.0 的门槛，不能因超时悄悄取消。

### U2 — 三个页面足够完成主要工作

建议预算 2–3 日，复用现有页面，不另建复杂设计系统。

- 记录列表：稳定分页、按名称/状态/时间的最小过滤、清楚区分示例/用户记录；不再只有最近 100 条且无法找回。
- 记录详情：任务结果、已知用量/覆盖缺口、步骤列表、错误详情、疑点到证据的跳转。
- 比较页：选择基线和候选、解释不可比原因、展示质量与效率，不新增独立“实验管理”产品。
- 稳定 trace 链接及浏览器刷新/返回可用；本地链接不是可公开共享的云链接。
- loading/empty/offline/not-found/invalid-data 明确区分；不可把 Collector 离线展示成“没有记录”。
- 长文本、键盘焦点、基本对比度和不只靠颜色传达状态可用；先支持桌面，不做完整移动端或多语言系统。

验收：一个不熟悉 UI 的人可以找记录、找到疑点、返回列表、进行比较；记录帮助次数和最卡步骤。截图在真实数据流后拍，不以静态 mock 代替交付。

### U3 — 内容控制与最小数据管理

建议预算 2–3 日。任何外部试用前，敏感内容边界必须清楚；若更早试用，提前实施其中的采集关闭/脱敏部分。

- 显式控制 prompt、response、工具参数/结果、error stack 的采集；有 metadata-only 模式或等价的明确开关。
- 脱敏在出应用前完成；示例禁止采集 Authorization/API key。回调/规则失败时不回退为发送原始敏感内容。
- 不能承诺通用正则能识别所有秘密；说明本地数据库也可能包含敏感信息，浏览器与导出同样受影响。
- 内容未采集时 UI 显示缺失，相关诊断降级；不能为指纹比较绕过用户隐私设置。指纹也不是匿名化保证。
- 最小导出采用版本化、非执行 JSON，明确大小/字段限制。P3 已选择 MAMR 专用导入作为取证路径，先处理重复记录语义；通用第三方导入不在默认范围，绝不执行 trace 内代码或任意反序列化对象。
- 提供选中记录删除/明确的本地清理方法、数据库位置和备份说明；删除前确认目标，不默认自动清库。
- 不做云分享、自动上传遥测或复杂保留策略服务。

验收：包含假秘密的 fixture 在采集关闭/脱敏后不出现在 payload、数据库、UI、导出或日志；导出保留必要语义与来源。MAMR 导入须验证 round-trip、重复记录和错误版本；其他导入格式仍需单独证据。

### U4 — 独立首次使用取证

- 联系人和联系渠道须由用户授权；不得自行发送邀请。
- 至少两位不参与开发的人，从文档开始安装并接入自己的应用；记录环境、耗时、错误和帮助，不代操作后算成功。
- 先尝试允许他们停下来，真实卡住比被维护者救到成功更有信息价值。
- 优先修最常见的一到两个阻碍；无需为两位用户加入完整账号/设置系统。
- 每次试用只写简短事实记录；原始 trace 脱敏与共享须同意。

M4 退出：一条仓库外完整启动路径 + 两次独立首次使用 + 最小内容控制 + 记录/比较可用。无法招募时继续做已证实的修复，但标记产品门槛未完成，不假造“用户验证”。

## 11. M5：v1.0.0rc — 固定契约并解决真实可靠性风险

这一阶段不新增产品主功能。以下任务按实际前置依赖提前：例如导入重试前先做 R1，含敏感数据试用前先做 U3。

### R1 — 存储与交付语义

- trace、spans、warnings 的完成状态要么原子保存，要么具备明确可恢复状态；首选在现有 SQLite 内解决，不引入队列平台。
- 同 ID 同 payload 重复提交不重复计费/生成规则；同 ID 不同 payload 明确冲突，不静默覆盖。精确比较规则在实现片内定稿。
- 磁盘/事务失败、非法 payload、响应丢失、重复发送有故障注入测试；能区分“未保存”和“确认失败，状态未知”。
- 保留 strict flush 和显式 best-effort 语义；即便服务端支持幂等，也不顺手加入无限重试/后台线程。
- 在当前仅结束后发送的模式下，明确进程崩溃可能丢失未发送记录。不能宣传对所有尝试的完整审计。

### R2 — API、数据与兼容冻结

- 记录最小稳定 SDK/API/导出 schema 契约、错误类型、未知字段/版本处理和迁移规则。
- 旧 RAG fixture、旧 timing/score 数据、新效率记录均可读；升级不静默丢失本地数据库。
- 1.0 默认继续保留 raglens 及旧 env fallback；如果移除，须另有用户决定、公告和迁移窗口，不当作顺手清理。
- 核实受支持 Python/runtime OS/CPU 范围和依赖维护状态。当前声明并不自动等于 1.0 支持承诺；不能照抄旧 CI 矩阵。
- 一个源码真值驱动版本，或至少有一致性测试；不在多个文件手动改完后靠反复重建证明没漏。
- 不为所谓扩展性把现有 repo 切成多个服务/SDK 仓库；最小清晰边界即可。

### R3 — 支持范围、安全与最终验收

- 在声明支持的环境做 clean-install → 启动 → 自己的任务 → 查看/比较 → 停止/重启的数据保留检查。
- 有一条真正自动化的 SDK → Collector → Dashboard 浏览器验收，覆盖成功、异常、未知用量与主要导航；不是只有 API 测试加人工截图。
- 包元数据/安装/兼容、Go、Dashboard 和 runtime 发布产物在确切候选提交上验证；不复用旧提交的“全绿”。
- 重新检查依赖漏洞的版本、可达性和修复风险；已知高影响问题修复或明确阻断，不机械 audit fix 升级所有依赖。
- 验证 loopback、精确 CORS、输入大小与结构限制、UI 不执行 trace 内 HTML/脚本、文件导入不执行代码。
- 运行一组小而真实的容量检查：建议起点 1,000 条普通 trace、单条 100 个步骤，在记录的机器上评估列表/详情/比较。目标常规交互约 1 秒内；这是待测目标，不是已达性能。
- 测量 SDK 记录开销与显式 flush 耗时，分开报告；只优化已导致体验/SLO 失败的热点，不建完整 profiling 子项目。
- Docker 在可用宿主机上测后才能继续作为已验证路径；当前 WSL 限制不得变成反复修改用户系统的理由。
- README 展示当前真实结果、明确安装入口与限制；发布前刷新确实变化的截图。不改历史 release 的事实。

M5 退出：功能冻结；关键缺陷清零；支持矩阵和契约完整；候选版本仅做修复。发现需大改的产品需求返回选型，不混进 rc。

## 13. 顺序、预算与防止优化死循环

### 13.1 默认顺序与依赖

已发布 M0–M2 → P1/P2 → P3（必要 R1/隐私前置）→ P4/P5 → P6 → 产品价值复盘 → U1/U2/U3/U4 → R1/R2/R3 收口 → G1。P7 不阻塞这条主线；旧 E4 两条规则不再是 E5 的前置。

这是默认顺序而非机械流水线：R1 在任何重复导入/自动重试前完成；U3 在使用敏感数据前完成；U1 的短调查可以在 M3 接入阻力已明确时提前。不能借“提前做依赖”同时启动三个大模块。

P1–P6 暂估 10–16 个有效开发日，必要存储前置可能改变估算，P3 后必须重估；M4 暂留 6–10 日，M5 暂留 4–8 日。均非发布日期承诺，不含授权、招募、CI/发布等待和 rc 观察；P7 另计且可不做。

### 13.2 每片固定决策卡

范围压缩顺序：先删新增图表、第二供应商、第二框架、第二平台、通用导入，再删复杂自动化。不得删用量诚实性、敏感信息边界、旧数据兼容和真实验收来保住功能数量。异步/流式只在已选择应用需要时进入本版；一旦宣称支持，就必须验证，不能只写在文档里。

每次开工只写以下内容，通常 7–10 行就够：

1. 片号与用户结果：本片结束用户具体能多做哪件事？
2. 已确认阻碍：来自代码、复现还是用户反馈？假设须标记。
3. 已有能力：能复用哪些字段/组件/测试？
4. 最小改动与触及组件：哪个更小方案被比较过？
5. 不做什么：至少明确本片容易被拉进来的相邻功能。
6. 验收/证据：哪几个断言、哪个真实页面或命令输出？
7. 预算与停止：超过什么调查范围就先报告；通过什么就结束？

### 13.3 硬性防膨胀规则

- WIP = 1：同时只有一个主切片。当前结果没验证，不启动下一套架构。
- 一个切片通常 0.5–3 个有效开发日；超过 3 日先拆出可见垂直结果，不把“完成通用基础层”当作唯一交付。
- 一个原因不明的问题最多做两轮有新证据的方案尝试；仍不收敛就总结证据、缩小问题/请求方向，不反复换库试运气。必要安全修复不因此跳过。
- 实现接近原预算两倍，必须重新做决策卡并解释范围/阻碍，不默默加时。按父目标累计必要前置；拆片不重置预算，未知历史投入明确保留。
- 达到写定验收条件立即停止；代码风格、动画、抽象、额外边界仅在真实问题时继续。
- 连续两片没有可见用户结果，暂停新功能，检查是否把验证、文档或基础设施当成主线。
- 连续两个真实场景没有可行动收益，暂停效率诊断扩张；不以更多规则/适配器掩盖需求不成立。
- 相同未变产物不重复全量构建。因变更/错误需要重跑时说明哪条证据已失效。
- 里程碑冻结后只修阻断项；新功能移动到下一候选版本，不顺手搭车。

- 固定 MAMR/PydanticAI/RAG 三个对象，不再找第三个 Agent 框架。
- 不为重现已经丢失细节的随机错误反复付费；真实成功可验证采集，失败分支由 fixture 覆盖。
- 每次 live 先写问题、唯一主要变量、验收、调用/费用上限、停止点；历史 $0.50/$0.10 授权不是永久额度。
- 确定性分支测试、启发式留出集、结果比较各有证据标准；不把 8–12 个样本或全套重复实验套到每次文档/埋点修复。

| 变更 | 开发中 | 切片结束 | 集成/发布门槛 |
| --- | --- | --- | --- |
| 纯规划文档 | 链接/状态/术语检查 | git diff --check，确认只改文档 | 不重跑产品构建 |
| Dashboard 展示 | 受影响单元测试，尽早看页面 | Dashboard tests/build + 一次真实受影响流程 | 完整浏览器关键流程 |
| SDK 行为 | 相关 Python 测试 | Python 全套；公共 API/分发边界变更需 wheel/独立环境 | build、wheel、独立应用及声明矩阵 |
| Collector/存储 | 定向测试与失败注入 | go test ./... -count=1；协议变化做端到端 | 全栈兼容/数据升级/浏览器 |
| 启动/runtime | 进程生命周期定向测试 | startup tests + 可用宿主机 smoke | 仓库外 clean-install、支持平台、产物验证 |
| package README/metadata | 渲染和元数据核对 | 受影响包构建/检查 | 确切候选产物一次完整验证 |

每次报告准确命令、退出状态、结果与未覆盖项。不以“上次通过”冒充本次；也不因为改一行规划就跑全部发布流程。

### 13.5 文档分工，避免维护七份相同故事

- 本文件：产品假设、里程碑细纲、验收门槛。只在阶段决策变化时改。
- ROADMAP：短阶段状态/顺序入口；每片结束核对并只更新变化，链接本文件。旧里程碑移到日期快照，不复制测试日志。
- CURRENT_TASK：只保留当前片、固定父里程碑出口、累计已知/未知投入、本片结果及下一决策/停止点；旧任务归档，不累积测试历史。
- AI_HANDOFF：当前事实、未解决风险和实现入口；事实/接口边界变了才改，旧快照归档而非前插累积。
- DEVLOG：切片完成时一次简短执行证据；必要时链接原始测试记录。历史快照仅按需读取，不是下一步授权。
- DECISIONS：方向、契约、架构发生选择才追加，不逐次记录普通修补。
- NEXT_AGENT_BRIEF：读文档顺序和工作约定；不再因每个小提交重复维护版本历史。
- README/release notes：用户可用行为或发布状态变化时更新，不先宣传计划能力。

AGENTS 的验证与文档要求应与本节一致；发现冲突先澄清，不通过删必要测试节省时间。

## 14. 明确停车场：什么情况下才重新讨论

| 暂不做 | 重新进入的证据门槛 |
| --- | --- |
| 新增很多 provider/框架 adapters | 现有闭环有重复使用；至少两个真实应用被同一缺失集成阻挡 |
| 大规模跨领域 RAG 规则调优 | 目标用户真的依赖这些诊断，出现可复现误报/漏报；先为受影响规则留出样本 |
| agent DAG/流程编辑器 | 平铺步骤无法定位实际问题；简易父子树也不足 |
| 自动优化/LLM-as-judge | 手工比较已有收益，质量标准、成本上限和授权清楚；作为新里程碑 |
| live trace/部分上传/中途预算阻断 | 两个真实长任务因结束后采集无法解决需求；先评估是否改变产品定位 |
| 通用 OTLP/多平台导入导出 | 已有目标用户明确要迁移/复用现有 trace，薄映射可验证；不先造新标准 |
| offline 持久队列/自动重试 | 已确认交付丢失阻断使用；幂等与隐私边界先通过 |
| 云/团队/认证/账单 | 有明确协作需求、维护能力和独立授权；不塞进本地 1.0 |
| 多数据库/微服务/大规模性能优化 | 受支持工作负载的实测瓶颈，SQLite/单服务简单方案已不足 |
| 全平台 runtime、自动更新器 | 当前支持平台稳定且新增平台有用户与测试资源 |
| 全站改版、移动端、多语言 | 当前主要任务的可用性证据说明必要；不是因为觉得“不像成品” |

新增需求进入停车场时只记录：谁遇到、证据、阻碍哪一步、最小可能方案。没有这四项，不排期。

## 15. 阶段决策权与下次开工指示

助手负责：在已授权切片内选择最小实现、验证、展示结果、记录风险；主动拒绝无证据扩张；每个里程碑提供继续/收窄/暂停建议。

用户保留：目标用户/定位的大变化、付费 API 与预算、外部联系与数据共享、支持平台承诺、迁移性破坏、远端发布及任何重要范围扩大。

普通实现细节不重复请示。发现“只有重写后端才做得了”等方向性变化时先提供证据和备选，不自己扩大授权。

执行入口始终以 CURRENT_TASK 的下一片为准，依次完成验收、自检、DEVLOG、CURRENT_TASK 和 ROADMAP 进度更新后交付。无需重做接管审计、B1/B2 或 PyPI 准备。规划本身不改版本号，不开新发布，不把未来 agent 能力写成当前 README 事实。

最终判断标准：**1.0 是一个边界明确、别人愿意反复用来完成真实工作的工具，不是一个把所有热门 AI 概念装进去的版本号。**
