# SledTrace：通往 1.0 的产品与执行细纲

规划日期：2026-09-15。代码基线：1e77338，分支 codex/b2-independent-app-integration。

状态：**用户已于 2026-09-15 同意按此规划逐片开发；计划能力不等于已实现功能，也不是一次性执行或发布授权。** 当前完成状态以 ROADMAP/CURRENT_TASK 为准，不在本细纲复制每片执行日志。每次“继续开发”从 CURRENT_TASK 的一个切片开始，先写决策卡；不自动执行整张路线图。

## 0. 只读这一页，也能掌握方向

推荐定位：**面向 Python AI 应用开发者的本地执行效率诊断工具：看清一次任务的用量与耗时，定位疑似浪费，用同一任务的修改前后结果验证改进。**

不是重新开发 agent，也不是放弃 RAG。保留现有 RAG 证据模块，把产品主线从“这次回答为什么不对”扩展到“这次任务为什么贵、慢或失败；改完是否真的更好”。1.0 先服务单进程、可结束、可重复验证的 Python 工作流。

最重要的产品闭环：记录一次任务 → 找到具体步骤 → 查看证据 → 开发者修改应用 → 对比结果与开销。

| 阶段 | 唯一主要结果 | 候选版本归组 | 通过后才允许扩大什么 |
| --- | --- | --- | --- |
| M0：诚实基线 | 不把启发式常数显示成概率；保留已完成可靠性工作 | v0.7.1 发布决策独立处理 | 开始效率数据展示，不再扩展旧 RAG 规则 |
| M1：单次请求账本 | 用户能指出一次请求的 token 与时间花在哪 | v0.8 开发切片 E1 | 一条真实 agent 接入路径 |

| M3：证明改进 | 同任务、保留质量约束的一次可复核改进 | v0.8 产品门槛 E4–E5 | 投入独立 runtime 与更完整使用体验 |
| M4：别人能独立使用 | 无源码启动，能找到记录、比较、控制敏感内容 | v0.9 候选 U1–U4 | 稳定兼容和发布候选收口 |

| G1：正式 1.0 | 外部重复使用证据 + 所有硬门槛通过 | v1.0.0 | 不因版本数字顺手扩大平台范围 |

版本号是建议归组，不要求每个切片发版。M1–M3 是最先验证方向的一段；后半段只有通过产品价值门槛才投入。没有承诺发布日期。

三条不可妥协的规则：

1. 未知不写成零；疑似浪费不写成已证实浪费；更便宜不写成质量更好。
2. 每片结束交付能看见的结果，达到验收即停止。新想法进入停车场，不插队。
3. 没有真实使用证据时，缩小试验或停在 beta，不靠堆功能宣布 1.0。

## 1. 当前底牌：已有资产和真正缺口

以下是本地代码核对，不代表全部已经发布。最新已确认发布基线是 v0.7.0；v0.7.1 候选和 B1/B2 状态见 [AI_HANDOFF](../ai-context/AI_HANDOFF.md)。本轮没有重新查询远端发布状态，也没有重新执行产品测试。

| 已有资产 | 能节省什么 | 不能据此声称什么 |
| --- | --- | --- |
| Python SDK → Go → SQLite → React 链路 | 不必重写采集、存储和基本 UI | 不等于完整 agent 观测平台 |
| 已测/未知耗时、分数语义、显式 try_flush、本地网络边界 | 更可信的基础数据和失败行为 | 不等于自动可靠投递、零丢失或生产级安全 |
| llm 的 input_tokens/output_tokens/total_tokens metadata | E1 可以先展示已有数据 | 不是自动采集，也没有完整用量账本、价格库或通用计费 |
| wire/Go/SQLite 已有 parent_span_id | 后续层级可以增量接入 | Python 当前 llm/retrieval 均写 None，不能冒充嵌套 API |
| retrieval/llm span 与七类证据型规则 | 保留 RAG 的上下文检查能力 | 没有 tool/agent span；规则不是通用事实核查 |
| B1 启动预检、进程清理与 B2 仓库外 wheel 接入 | 不再重复基本安装/发布准备 | 内部独立环境不是外部用户；wheel 不含 runtime |
| CI、包发布、兼容测试和真实浏览器验收经历 | 发布和回归有基础 | 测试数量不能证明产品需求或诊断准确率 |

当前具体缺口：

- Dashboard 没有任务级用量概览、逐次调用计费、修改前后比较、稳定记录链接或分页。
- llm 记录方法目前总写 ok，且每次 response 会更新 trace answer；不能直接把“最后一次模型调用”当成 agent 任务结果。
- 业务异常可写入 trace metadata，但清晰的异常详情与失败尝试展示仍不完整。
- POST 接收完整 trace；没有运行中/部分上传、崩溃恢复或中途预算阻断。
- trace/spans 与 warnings 分两次事务保存；重复提交语义不完善。加入重试前必须先处理此边界。
- 固定 confidence 被显示为百分比；多条规则依赖英文词法及特定政策领域，没有广泛准确率证据。
- 当前纯 Python wheel 只安装 SDK/CLI；完整服务仍需源码和 Docker，或 Go/Node 工具链。
- 没有已记录的独立外部首次使用与重复使用证据；当前最缺的是这一类证据，不是另一个大模块。

主要代码入口：sdk/python/raglens/trace.py、collector/go/internal/api/handlers.go、collector/go/internal/storage/sqlite.go、dashboard/web/src/pages/TraceDetailPage.tsx。实现前读相关符号，不依赖旧文档行号。

## 2. 核心竞争力：资产、假设和证据分开

### 2.1 哪些不是护城河

“开源”“本地”“有 trace”“统计 token”“画 agent 图”都是有价值的属性，但不是独有优势。Langfuse 已有用量/成本跟踪和 agent 图能力；追赶这些功能的数量不是我们的获胜方法。[用量文档](https://langfuse.com/docs/observability/features/token-and-cost-tracking)、[Agent 图文档](https://langfuse.com/docs/observability/features/agent-graphs)，核对于 2026-09-15。

研究也已经探索成本归因与 agent 修改。ClawTrace 的研究报告中，跨完整 SkillsBench 迁移并没有取得总成本节省；这提醒我们不能把“给出优化建议”当成“稳定产生收益”。这是该研究的结果，不是对所有 agent 的结论。[ClawTrace v2](https://arxiv.org/abs/2604.23853v2)，核对于 2026-09-15。

### 2.2 我们值得验证的差异化

| 候选优势 | 对用户的具体好处 | 目前证据 | 达到什么才可以对外宣传 |
| --- | --- | --- | --- |
| 短反馈闭环 | 不用从大量 trace 自己推导下一步 | 有 RAG 证据展示基础，效率闭环未实现 | 用户从疑点跳到调用，再用对比决定保留/撤销修改 |
| 诚实、可核查的效率诊断 | 不会被“省了 40%”或“90% 置信度”误导 | 时序和分数诚实性已改进 | 用量来源、覆盖缺口、价格依据、比较限制均可见 |
| 轻量本地接入 | 无账号，敏感内容可留本机，不改应用执行方式 | 本地架构已有，启动仍复杂 | 仓库外安装启动通过，内容控制通过独立试用 |
| 框架边界薄 | 自写 agent 也能用，不为换框架重接整个系统 | 手动 Python API 可用 | 一个真实应用接入，第二个可复用而无需核心分叉 |
| RAG 与工具证据相连 | 看清检索/工具返回如何导致多余调用 | retrieval 模块已有，tool 路径缺失 | 在一个真实检索型 agent 中帮助定位具体开销 |

这些是产品假设，不是已经形成的壁垒。更可持续的积累是：真实且可脱敏复现的问题样本、可靠的计量/比较契约、低摩擦接入经验，以及用户愿意再次打开它的工作流。样本未经允许不得集中上传。

### 2.3 为什么保留这个项目，而不是重开一个

- 已有组件与目标任务基本吻合，改产品重心不要求换技术栈或品牌。
- retrieval 仍是 agent 常用的一类步骤；RAG 资产可以继续贡献证据，不必成为唯一定位。
- 模型、框架会变，“观察实际执行 → 衡量结果 → 验证修改”的问题更稳定。但这只是长期需求判断，不保证我们会获得用户。
- 不以“领先某个大平台”为目标；先证明小范围用户用 SledTrace 比自己的日志/表格更快得到一个有用结论。

## 3. 目标用户与 1.0 的明确边界

### 首要用户

维护 Python AI 应用的独立开发者或小团队：已有一个能运行的 RAG/工具型 agent，能改应用代码，有可重复的任务和质量验收，但不知道增加检索、工具或重试后为什么更贵、更慢。

首个试验选择一个短时、单进程、可重复运行的工作流，优先已有真实需求的知识检索/资料处理 agent。不得为了让诊断显得有效而只造一个故意无限循环的演示。

首批不服务：纯聊天消费者、不能改代码的 SaaS 使用者、跨服务大型集群、需要线上 SLA/权限审计/多租户的组织、要求无人值守自我改进的 agent 平台。

### 1.0 承诺的能力

- 观察已接入的 Python 工作流，不宣称自动覆盖电脑上或账号里的全部 AI 调用。
- 查看已提交、已结束的任务；包括成功、失败以及有证据记录的取消/不完整状态。
- 逐次 LLM 用量与工具耗时、错误、可追溯证据；使用者知道哪些调用没有用量数据。
- 两种保守、可禁用的疑似浪费提示；没有满足前提就不下判断。
- 同任务、同验收规则的前后比较，展示质量、成本、时间及不可比项。
- 支持矩阵内无需源码的本地启动，SDK 仍可单独安装使用。
- 有限数据管理、敏感内容控制、兼容承诺和可读错误；无需云账号。

### 1.0 明确不承诺

- 完整 harness/agent runtime、自动规划执行、自动改 prompt/代码并上线。
- 读取私有思维链，或从轨迹推断模型“真正为什么这样想”。
- 完整运行中监控、中途停止失控 agent、部分上传/断点续传、进程崩溃零丢失。
- 自动识别所有框架、所有模型的精确账单，或同步用户供应商账单。
- 多 agent 通信图编辑器、分布式追踪、实时 GPU/本地电费归因。
- 通用 LLM-as-judge、完整实验平台、提示词注册中心、任意代码重放系统。
- 云托管、认证、团队权限、支付计费、全平台全架构 runtime。

如果试用显示“必须实时阻止长任务烧钱”才有价值，应重新选择范围；不能边称已完成本计划，边悄悄接入一个运行时控制系统。

## 4. 衡量价值，而不是衡量忙碌

北极星记录单位：**开发者完成一次“发现问题—修改—验证—决定保留或撤销”的闭环。** 成本不降但及时发现质量退步，也可以是有用结果；不能算作已实现节省。

| 指标 | 测量办法 | 建议目标/决策用途 |
| --- | --- | --- |
| 首次成功 | 从准备环境、安装、埋点到第一条自己的 trace，分别计时 | 满足声明前置条件后 ≤10 分钟；总设置时间另外报告 |
| 接入阻力 | 记录修改位置、配置数、需帮助步骤、失败原因 | 最常见工作流约 3 个埋点位置；不靠删必要校验凑行数 |
| 数据可信 | 原始 provider usage 与显示结果逐项对照 | 所支持来源的测试样本精确一致，缺失明确显示 |
| 找到疑点 | 从打开记录到指出具体可行动调用，记录实际时间 | 初步目标 ≤5 分钟；超时先查界面/信息问题 |
| 有用诊断 | 用户认领/否认提示，并说明采取何种修改 | 收集原因与反例，不追求报警数量 |
| 有效比较 | 固定任务、输入版本、验收、环境，保存 A/B 结果 | 保留失败项、计量缺口和样本数，不只展示最佳一次 |
| 重复使用 | 不由维护者代操作，在另一天/另一个修改后再次使用 | 1.0 门槛：至少 2 位独立开发者有此证据 |

这些门槛是小项目的产品决策门槛，不是统计显著性或市场规模证明。Star、下载数、测试数和发版数可以记录，但不替代上述证据。

## 5. 计量与诊断契约：先把容易做错的地方写死

### 5.1 用量、金额和时间

- 优先记录供应商响应给出的 usage，保留来源/模型标识/采集方式；手工输入、离线 fixture、估算必须区分。
- 保留 input/output 和 provider 的细分含义。cached/reasoning 可能是包含关系，不能不核对来源就再次相加。
- 每个真实尝试单独记录。失败调用有 usage 就计入；没有返回 usage 是未知，不是免费。供应商 SDK 隐藏重试是已知覆盖缺口。
- 聚合只对已计量的唯一调用求和；父步骤汇总不能再与子调用相加。重复投递也不能重复记账。
- 显示“已知小计 + 缺失调用数/已观察调用数”，不是只有一个看似完整的总数；未埋点的调用数量本身可能未知。
- total_tokens 可能缺少分项；不凭总数反推 input/output。非法、负数或冲突数据要有明确拒绝/降级策略。
- 成本至少带币种、价格来源、价格快照日期/版本、计费类别与估算标签。初期只支持一个明确来源，或用户显式价格；无法可靠定价就显示未知。
- 不在每次打开旧记录时套用今天价格而悄悄改写历史。重算必须是显式操作并保留原依据。
- token 减少不等于费用减少；缓存、服务档位、工具费用和模型价格不同。未接入的工具费用单独列为未知范围。
- 本地模型 usage 可以计数，但金额默认未知；不擅自折算电费/GPU 成本。
- 墙钟耗时来自任务边界；并行 span 时长不能相加当作任务耗时。只知道持续时间时，不伪造真实开始点或“独占耗时”。

### 5.2 三个绝不混用的结论层级

| 层级 | 可以说 | 不可以说 |
| --- | --- | --- |
| 观察事实 | 3 次调用参数与返回指纹一致，已知消耗 X | 这 3 次全部无用 |
| 疑似可优化 | 满足指定规则，建议检查重试/缓存/停止条件 | 必然可以节省 X，或模型推理错误 |
| 经比较的结果 | 在给定任务与验收下，B 比 A 少消耗 X，样本为 N | 对所有任务都能节省该比例 |

相同请求可能是必要轮询、故障恢复或独立确认。状态未知时写“不可判断是否重复劳动”。不得把没有新文本当成没有进展。

### 5.3 质量与完整性

- 执行状态与任务是否成功分开：程序返回 ok，不等于回答正确/任务完成。
- 用任务自己的确定性验收、人工标签或已有评估结果；记录标准版本、来源与未评估状态。
- 失败、取消、交付失败与用量缺失的记录保留在比较分母里，不能只选两边成功样本。
- 自动测例用于验证实现；真实工作流用于验证价值。内部维护者使用、外部用户使用分别标注。
- 初期没有自动执行任意应用的能力。开发者自行完成两次运行，SledTrace 比较结果；有付费调用或外部副作用必须先明确授权。

## 6. M0：诚实基线与已有工作收口

### H0 — 下一片：移除伪概率展示

价值：在增加新诊断前，先让现有提示不误导用户。建议实现预算半天至 1 个有效开发日。

- 修改现有 warning UI，不再把固定 confidence 显示为校准概率百分比。
- 保留规则类型、严重程度、证据和适用限制；未知字段不妨碍旧数据渲染。
- 不把百分比换成没有依据的“高可信”；可展示明确的启发式提示及原始字段的技术语义。
- 验收：有/无 confidence、非法值、旧 payload 均能呈现；真实页面能看到前后区别，证据未丢。
- 测试：相关 UI 单元测试、Dashboard build、一次真实浏览器验收。
- 不做：新规则、准确率校准、大规模跨领域样本、UI 整体改版、SDK/runtime 变更。
- 停止：上述验收通过即转 E1，不用一周润色 warning 文案。

### A0 — 发布整理是旁路，不是新的功能阶段

- 已完成的 S1–S4、B1/B2 不重做；在下一次获准整合/发布时重新核对 Git/PR/CI 状态。
- v0.7.1 原候选 PR 和 B1/B2 后续提交分别处理；不能把本地工作默认为远端已发布。
- 首次受影响发布时对齐 package README 的候选安装说明，避免未发布版本被描述为可直接安装。
- 不因为每个 UI 小片都重建包、重新上传测试索引或重复验证历史发布流程。
- 远端合并、tag、PyPI、GitHub Release 仍需当轮或延续范围内的明确授权。

M0 退出：H0 完成，下一片 E1 已写明；没有必要等待新的发布审批才做局部产品开发。

## 7. M1：单次请求账本，不先建 agent 框架

### E1 — 看见现有 LLM 用量与耗时

建议预算 1–2 个有效开发日。主要修改 Dashboard，只有现有接口无法表达必要事实时才补最小契约。

- 使用当前 llm metadata，增加任务级用量小计和逐次调用明细。
- 显示模型、调用顺序、input/output/total、实测/未知耗时、用量来源缺失提示。
- 处理多次调用、仅 total、零值、完全缺失、非法值、元数据冲突；旧 trace 可继续查看。
- 只在可比且完整的数值上排序；缺失不排成“最省”，不能把不同 token 类别混成金额。
- 使用一个现有请求及受控 fixture 验证；不新增 agent/tool 类型、不接自动价格服务。

验收与可见证据：

1. 一个含多次 llm 的 trace，小计与逐次数据可手算核对。
2. 一个部分缺失数据的 trace，页面明确说“小计/未知”，没有虚假 0。
3. 点击最贵的已知 token 调用可看到原 prompt/response 或内容未采集状态。
4. 聚合/非法数据的定向测试、Dashboard build 及真实页面检查通过。

退出决策：如果这张表已解决试用者的问题，可以先以“执行分析器”交付；若只是多一组数字，继续 M2/M3 验证行动价值，不用先做十种图表。

## 8. M2：一条真实 agent 接入路径

### E2 — 可辨认的 LLM/工具尝试与任务结果

建议预算 2–3 个有效开发日。进入条件：选定一个真实工作流及其执行边界。没有可用真实应用时，先做内部可运行示例，但价值验收保持未完成。

- 初期选普通 Python、一个进程、一层工具调用；不强制接框架。
- 只新增本场景必需的 tool 记录能力；名称、输入/输出摘要或指纹、状态、错误、测量与 span ID 可核对。
- LLM 失败尝试有正确状态与已有 usage，恢复成功的任务可仍为成功；区分单步错误和最终任务结果。
- 明确 task_id/case_id、variant、run_id、应用版本、验收结果的最小关联方式，优先增量字段，避免新建实验系统。
- 最终任务输出由应用显式记录，不再依赖“最后一条 LLM response”。保留旧 RAG API 的兼容行为。
- 只有示例真的需要父子关联时，才接通已有 parent_span_id；不同时新增 agent/memory/retry/rerank 等 span 家族。
- async 应用是首个样本时须测试上下文隔离；否则同步路径先交付，禁止以“已支持所有 async/thread”宣传。

验收：一次多轮 LLM + 工具的成功任务、一次业务失败、一次工具失败后恢复；API 读回和 UI 对齐，不能串 trace。旧 RAG fixture、SDK 公共调用与未知 span 展示退路通过。

可见结果：用户能顺着步骤列表找到具体失败/重复调用和最终任务结果，不需要复杂 DAG。

### E3 — 一个来源的可靠 usage 与价格依据

建议预算 1–2 个有效开发日。选择 E2 应用实际使用的供应商/客户端，不预先承诺所有模型。

- 在显式调用边界读取 usage；如必须依赖供应商 SDK，放可选依赖/薄集成，不增加核心 SDK 强制依赖。
- 只验证该来源和版本的 input/output/cache/reasoning 包含关系，保存计量来源与缺口。
- 原始供应商响应的脱敏 fixture 用于 CI；真实调用只在获得 API 访问/费用授权后进行。
- 选一种价格输入：版本化的单来源配置或用户明确输入；标签必须是估算，不承诺与最终账单完全一致。
- 流式调用若是目标用户必需，先覆盖结束时 usage 和中断缺失；不为此增加 Collector 实时流协议。否则延后。
- 隐式重试无法观察就展示限制，不做 monkey-patch 全部网络客户端来追求虚假的全覆盖。

验收：同一调用的来源数据、持久化值、UI 和金额计算逐项一致；缓存/缺失/失败/重复归属不会双算。集成测试默认不联网、不收费。

M2 退出：至少一条实际工作流可观测；数据缺口有明确说法。接入过重时先减少封装层，不立即添加另一套框架适配器。

## 9. M3：先证明一次改进，再建更大的诊断系统

### E4 — 两类保守的疑似浪费提示

建议预算 1–2 个有效开发日。只选以下两类，不按“凑规则数”扩展：

| 规则 | 所需证据 | 必须包含的反例 |
| --- | --- | --- |
| 相同工具调用重复返回相同结果 | 相同工具/规范化参数/结果指纹、步骤引用；已知状态/时间范围 | 正常轮询、外部状态变化、必要确认、不可见状态 |
| 同一错误在条件未改变时重复出现 | 错误类别/可比较摘要、参数、尝试序列、可用状态证据 | 临时限流后重试成功、退避、参数修复、状态改变 |

- 只对可解释的字段做规范化，不用模糊语义相似度自动宣布“相同”。
- 标题写“疑似重复/建议检查”，显示触发条件、相关调用、已知消耗和不能下结论的原因。
- 不能确认状态时降级为观察提示/不判定；没有内容授权时不为生成指纹偷偷记录原文。
- 每条规则支持关闭/忽略的最低可用方式；人工“有用/无用”反馈可先人工记录，不建反馈平台。
- 初始每条约 8–12 个正反/边界样本，其中一部分在规则修改前留出；报告具体数量，不宣称通用准确率。

验收：至少一个触发例和两个合理重复反例真实可见；从提示定位原调用；同一 fixture 重复分析稳定。规则没有证据价值时删除/禁用，不追加补丁直到演示全绿。

### E5 — 任务结果约束下的 A/B 比较

建议预算 2–3 个有效开发日。开发者自行运行 A/B；SledTrace 不执行或重放外部工具。

- 先做两次 run 并排比较：同 case、输入/环境版本、variant、验收结果、调用数、已知 token、估算费用、墙钟时间。
- 显示发生变化的步骤与原始证据，不只给一个“优化分数”。旧 warning 数减少不等于答案更正确。
- 比较资格显式判断：不同任务、计量缺失、验收改变、环境差异时警告或不给百分比。
- 基线为 0/未知时不给误导性百分比；不同币种不自动换算；不同模型可比任务结果，但不当成只改一个参数的因果实验。
- 初步试验用 3–5 个固定任务，每个版本每任务至少 3 次；昂贵/不可重复任务由用户选择更小预算并标明不足。此数量只支持小规模决策。
- 锁定验收标准再改应用；保存全部尝试，展示范围/中位数、样本数和质量通过情况。能固定 seed 就记录，但不声称完全可复现。
- 先输出页面与简单 Markdown/JSON 摘要即可，不建实验调度、排行榜或统计服务。

M3 产品门槛：

1. 至少一个不是故意注入循环的真实问题，由记录引导一次具体修改。
2. 结果可复核：质量不低于预先选定标准且开销改善；或识别出“变便宜但质量下降”，帮助撤销修改。
3. 使用者能解释为什么保留/撤销这次改动，不由助手代替判断。
4. 未达成“质量保持且效率改善”时，不能宣传已实现节省；可以因可靠回归检测继续小规模试用。

通过后才把 v0.8 作为效率闭环候选发布。未通过时最多再选一个更匹配的真实场景，仍无行动价值则收窄为账本/比较工具或暂停该方向；不要靠第三种 agent 框架推迟判断。

## 10. M4：v0.9 — 让别人不用我们陪着也能使用

### U1 — 去掉完整产品对源码仓库的依赖

先做最多 1–2 日可行性调查，随后一次 2–3 日的最小实现片。首选复用现有 Go Collector + 内嵌构建后的静态 Dashboard；这是待验证的分发方案，不是已交付架构。

- 比较预编译独立 runtime、平台 wheel/可选安装包的维护成本；只选一种主路径。
- 理想用户结果：安装 SDK；明确安装/取得本地 runtime；一个命令启动并获得可点击地址。不要求用户安装 Go、Node 或克隆源码。
- 不把“必须恰好只有一个 pip 命令”当作架构约束；SDK 轻量可单独使用，完整产品可以有清楚的第二步。
- 如果需要下载可执行文件，用户必须知情，绑定可信发布来源、版本和 checksum；不默默下载 latest 并执行。首次下载与之后离线启动分开测试。
- 先定一个有 CI 和实际试用设备的平台组合；增加第二个平台需有测试资源。Windows 是当前用户环境，但现有 SQLite 驱动的可构建性必须先核对。
- 显示 runtime/SDK 版本、服务地址、数据库位置；启动失败可操作，退出只清理由自己创建的进程。
- 默认 loopback，不打开局域网服务；适配静态 UI 的 API 路由，不为一个页面保留不必要的双服务端口。
- 测试：全新环境、仓库外安装、启动、关闭、再次启动、已占端口、离线已安装启动、不支持平台提示、数据保留。

退出条件：一条无需源码的支持路径可重复。超过调查预算就提交方案/阻碍，选择手动安装独立 runtime 或收窄平台；不重写 Python backend，不拖着不决。该能力仍是完整产品 1.0 的门槛，不能因超时悄悄取消。

### U2 — 三个页面足够完成主要工作

建议预算 2–3 日，复用现有页面，不另建复杂设计系统。

- 记录列表：稳定分页、按名称/状态/时间的最小过滤、清楚区分示例/用户记录；不再只有最近 100 条且无法找回。
- 记录详情：任务结果、已知用量/覆盖缺口、步骤列表、错误详情、疑点到证据的跳转。
- 比较页：选择基线和候选、解释不可比原因、展示质量与效率，不新增独立“实验管理”产品。
- 稳定 trace 链接及浏览器刷新/返回可用；本地链接不是可公开共享的云链接。
- loading/empty/offline/not-found/invalid-data 明确区分；不可把 Collector 离线展示成“没有记录”。
- 长文本、键盘焦点、基本对比度和不只靠颜色传达状态可用；先支持桌面，不做完整移动端或多语言系统。

验收：一个不熟悉 UI 的人可以找记录、找到疑点、返回列表、进行比较；记录帮助次数和最卡步骤。截图在真实数据流后拍，不以静态 mock 代替交付。

### U3 — 内容控制与最小数据管理

建议预算 2–3 日。任何外部试用前，敏感内容边界必须清楚；若更早试用，提前实施其中的采集关闭/脱敏部分。

- 显式控制 prompt、response、工具参数/结果、error stack 的采集；有 metadata-only 模式或等价的明确开关。
- 脱敏在出应用前完成；示例禁止采集 Authorization/API key。回调/规则失败时不回退为发送原始敏感内容。
- 不能承诺通用正则能识别所有秘密；说明本地数据库也可能包含敏感信息，浏览器与导出同样受影响。
- 内容未采集时 UI 显示缺失，相关诊断降级；不能为指纹比较绕过用户隐私设置。指纹也不是匿名化保证。
- 最小导出采用版本化、非执行 JSON，明确大小/字段限制。导入不是默认 1.0 必做项；只有真实离线交接需求成立时才补，并先处理重复记录语义，绝不执行 trace 内代码或任意反序列化对象。
- 提供选中记录删除/明确的本地清理方法、数据库位置和备份说明；删除前确认目标，不默认自动清库。
- 不做云分享、自动上传遥测或复杂保留策略服务。

验收：包含假秘密的 fixture 在采集关闭/脱敏后不出现在 payload、数据库、UI、导出或日志；导出保留必要语义与来源。如果选择导入，再验证 round-trip、重复记录和错误版本；未选择就不开发。

### U4 — 独立首次使用取证

- 联系人和联系渠道须由用户授权；不得自行发送邀请。
- 至少两位不参与开发的人，从文档开始安装并接入自己的应用；记录环境、耗时、错误和帮助，不代操作后算成功。
- 先尝试允许他们停下来，真实卡住比被维护者救到成功更有信息价值。
- 优先修最常见的一到两个阻碍；无需为两位用户加入完整账号/设置系统。
- 每次试用只写简短事实记录；原始 trace 脱敏与共享须同意。

M4 退出：一条仓库外完整启动路径 + 两次独立首次使用 + 最小内容控制 + 记录/比较可用。无法招募时继续做已证实的修复，但标记产品门槛未完成，不假造“用户验证”。

## 11. M5：v1.0.0rc — 固定契约并解决真实可靠性风险

这一阶段不新增产品主功能。以下任务按实际前置依赖提前：例如导入重试前先做 R1，含敏感数据试用前先做 U3。

### R1 — 存储与交付语义

- trace、spans、warnings 的完成状态要么原子保存，要么具备明确可恢复状态；首选在现有 SQLite 内解决，不引入队列平台。
- 同 ID 同 payload 重复提交不重复计费/生成规则；同 ID 不同 payload 明确冲突，不静默覆盖。精确比较规则在实现片内定稿。
- 磁盘/事务失败、非法 payload、响应丢失、重复发送有故障注入测试；能区分“未保存”和“确认失败，状态未知”。
- 保留 strict flush 和显式 best-effort 语义；即便服务端支持幂等，也不顺手加入无限重试/后台线程。
- 在当前仅结束后发送的模式下，明确进程崩溃可能丢失未发送记录。不能宣传对所有尝试的完整审计。

### R2 — API、数据与兼容冻结

- 记录最小稳定 SDK/API/导出 schema 契约、错误类型、未知字段/版本处理和迁移规则。
- 旧 RAG fixture、旧 timing/score 数据、新效率记录均可读；升级不静默丢失本地数据库。
- 1.0 默认继续保留 raglens 及旧 env fallback；如果移除，须另有用户决定、公告和迁移窗口，不当作顺手清理。
- 核实受支持 Python/runtime OS/CPU 范围和依赖维护状态。当前声明并不自动等于 1.0 支持承诺；不能照抄旧 CI 矩阵。
- 一个源码真值驱动版本，或至少有一致性测试；不在多个文件手动改完后靠反复重建证明没漏。
- 不为所谓扩展性把现有 repo 切成多个服务/SDK 仓库；最小清晰边界即可。

### R3 — 支持范围、安全与最终验收

- 在声明支持的环境做 clean-install → 启动 → 自己的任务 → 查看/比较 → 停止/重启的数据保留检查。
- 有一条真正自动化的 SDK → Collector → Dashboard 浏览器验收，覆盖成功、异常、未知用量与主要导航；不是只有 API 测试加人工截图。
- 包元数据/安装/兼容、Go、Dashboard 和 runtime 发布产物在确切候选提交上验证；不复用旧提交的“全绿”。
- 重新检查依赖漏洞的版本、可达性和修复风险；已知高影响问题修复或明确阻断，不机械 audit fix 升级所有依赖。
- 验证 loopback、精确 CORS、输入大小与结构限制、UI 不执行 trace 内 HTML/脚本、文件导入不执行代码。
- 运行一组小而真实的容量检查：建议起点 1,000 条普通 trace、单条 100 个步骤，在记录的机器上评估列表/详情/比较。目标常规交互约 1 秒内；这是待测目标，不是已达性能。
- 测量 SDK 记录开销与显式 flush 耗时，分开报告；只优化已导致体验/SLO 失败的热点，不建完整 profiling 子项目。
- Docker 在可用宿主机上测后才能继续作为已验证路径；当前 WSL 限制不得变成反复修改用户系统的理由。
- README 展示当前真实结果、明确安装入口与限制；发布前刷新确实变化的截图。不改历史 release 的事实。

M5 退出：功能冻结；关键缺陷清零；支持矩阵和契约完整；候选版本仅做修复。发现需大改的产品需求返回选型，不混进 rc。

## 12. G1：正式 1.0 的 go/no-go 清单

以下全部通过才建议发布“完整产品 1.0”；勾选需要链接到真实证据，不能用计划文字作为证据。

- [ ] 目标用户与支持范围明确；对外不宣称完整 agent 平台或私有推理分析。
- [ ] 一条非源码本地安装启动路径在声明平台上可重复，SDK 可单独使用。
- [ ] 一个实际多步 Python 应用接入，LLM/工具/失败尝试/最终结果清楚，RAG 兼容未破坏。
- [ ] 用量来源、小计/缺口、费用估算依据正确；没有已知双算、未知写零或假置信度问题。
- [ ] 两类保守提示有正反/留出样本，或有证据决定禁用无价值规则，产品说明同步收窄。
- [ ] 至少一个真实任务完成可核查的质量约束改进；若只有回归识别，没有效率改善，先以明确收窄的 beta 定位继续验证。
- [ ] 至少两位独立开发者各完成首次使用，并在另一天/另一项修改中自行再次使用；与内部演示分开。
- [ ] 隐私控制、错误处理、重复提交、持久化、旧数据读取与受支持升级通过。
- [ ] CI、clean-wheel/runtime、真实自动浏览器链路以及一次人工视觉检查基于同一候选通过。
- [ ] rc 观察窗口建议 7–14 个日历日，期间有真实使用且无未解决的阻断级问题；单纯等待天数不算验证。
- [ ] 已知限制、发布说明、支持矩阵和数据备份/恢复指引可读；无虚构用户反馈或过时演示。
- [ ] 用户明确批准当次 merge/tag/发布操作，并通过既有保护流程。

没有达到外部使用门槛，并不等于代码没价值；可以继续发清楚标注的 beta。但不能把“工程完成”包装为“产品已被验证”。

## 13. 顺序、预算与防止优化死循环

### 13.1 默认顺序与依赖

H0 → E1 → 选择真实工作流 → E2 → E3 → E4 → E5 → 产品价值复盘 → U1/U2/U3/U4 → R1/R2/R3 → G1。

这是默认顺序而非机械流水线：R1 在任何重复导入/自动重试前完成；U3 在使用敏感数据前完成；U1 的短调查可以在 M3 接入阻力已明确时提前。不能借“提前做依赖”同时启动三个大模块。

M0–M3 的建议实现总量约 8–14 个有效开发日；M4/M5 仅作后续 10–18 日的粗量级预留。不是交付承诺，不含招募、授权、远端 CI/发布等待和 rc 观察；到 M3 必须重新估算，不能把不确定性藏进排期。

### 13.2 每片固定决策卡

范围压缩顺序：先删新增图表、第二供应商、第二框架、第二平台、可选导入，再删复杂自动化。不得删用量诚实性、敏感信息边界、旧数据兼容和真实验收来保住功能数量。异步/流式只在已选择应用需要时进入本版；一旦宣称支持，就必须验证，不能只写在文档里。

每次开工只写以下内容，通常 7–10 行就够：

1. 片号与用户结果：本片结束用户具体能多做哪件事？
2. 已确认阻碍：来自代码、复现还是用户反馈？假设须标记。
3. 已有能力：能复用哪些字段/组件/测试？
4. 最小改动与触及组件：哪个更小方案被比较过？
5. 不做什么：至少明确本片容易被拉进来的相邻功能。
6. 验收/证据：哪几个断言、哪个真实页面或命令输出？
7. 预算与停止：超过什么调查范围就先报告；通过什么就结束？

### 13.3 硬性防膨胀规则

- WIP = 1：同时只有一个主切片。当前结果没验证，不启动下一套架构。
- 一个切片通常 0.5–3 个有效开发日；超过 3 日先拆出可见垂直结果，不把“完成通用基础层”当作唯一交付。
- 一个原因不明的问题最多做两轮有新证据的方案尝试；仍不收敛就总结证据、缩小问题/请求方向，不反复换库试运气。必要安全修复不因此跳过。
- 实现接近原预算两倍，必须重新做决策卡并解释范围/阻碍，不默默加时。
- 达到写定验收条件立即停止；代码风格、动画、抽象、额外边界仅在真实问题时继续。
- 连续两片没有可见用户结果，暂停新功能，检查是否把验证、文档或基础设施当成主线。
- 连续两个真实场景没有可行动收益，暂停效率诊断扩张；不以更多规则/适配器掩盖需求不成立。
- 相同未变产物不重复全量构建。因变更/错误需要重跑时说明哪条证据已失效。
- 里程碑冻结后只修阻断项；新功能移动到下一候选版本，不顺手搭车。

### 13.4 比例化测试，不削弱发布验收

| 变更 | 开发中 | 切片结束 | 集成/发布门槛 |
| --- | --- | --- | --- |
| 纯规划文档 | 链接/状态/术语检查 | git diff --check，确认只改文档 | 不重跑产品构建 |
| Dashboard 展示 | 受影响单元测试，尽早看页面 | Dashboard tests/build + 一次真实受影响流程 | 完整浏览器关键流程 |
| SDK 行为 | 相关 Python 测试 | Python 全套；公共 API/分发边界变更需 wheel/独立环境 | build、wheel、独立应用及声明矩阵 |
| Collector/存储 | 定向测试与失败注入 | go test ./... -count=1；协议变化做端到端 | 全栈兼容/数据升级/浏览器 |
| 启动/runtime | 进程生命周期定向测试 | startup tests + 可用宿主机 smoke | 仓库外 clean-install、支持平台、产物验证 |
| package README/metadata | 渲染和元数据核对 | 受影响包构建/检查 | 确切候选产物一次完整验证 |

每次报告准确命令、退出状态、结果与未覆盖项。不以“上次通过”冒充本次；也不因为改一行规划就跑全部发布流程。

### 13.5 文档分工，避免维护七份相同故事

- 本文件：产品假设、里程碑细纲、验收门槛。只在阶段决策变化时改。
- ROADMAP：一页入口/状态与历史里程碑；每片结束更新进度，链接本文件，不重复细纲。
- CURRENT_TASK：每片结束更新本片结果、下一片行动卡和停止点，不累积全部测试历史。
- AI_HANDOFF：当前事实、未解决风险和实现入口；状态/接口边界变了才改。
- DEVLOG：切片完成时一次简短执行证据；必要时链接原始测试记录。
- DECISIONS：方向、契约、架构发生选择才追加，不逐次记录普通修补。
- NEXT_AGENT_BRIEF：读文档顺序和工作约定；不再因每个小提交重复维护版本历史。
- README/release notes：用户可用行为或发布状态变化时更新，不先宣传计划能力。

AGENTS 的验证与文档要求应与本节一致；发现冲突先澄清，不通过删必要测试节省时间。

## 14. 明确停车场：什么情况下才重新讨论

| 暂不做 | 重新进入的证据门槛 |
| --- | --- |
| 新增很多 provider/框架 adapters | 现有闭环有重复使用；至少两个真实应用被同一缺失集成阻挡 |
| 大规模跨领域 RAG 规则调优 | 目标用户真的依赖这些诊断，出现可复现误报/漏报；先为受影响规则留出样本 |
| agent DAG/流程编辑器 | 平铺步骤无法定位实际问题；简易父子树也不足 |
| 自动优化/LLM-as-judge | 手工比较已有收益，质量标准、成本上限和授权清楚；作为新里程碑 |
| live trace/部分上传/中途预算阻断 | 两个真实长任务因结束后采集无法解决需求；先评估是否改变产品定位 |
| 通用 OTLP/多平台导入导出 | 已有目标用户明确要迁移/复用现有 trace，薄映射可验证；不先造新标准 |
| offline 持久队列/自动重试 | 已确认交付丢失阻断使用；幂等与隐私边界先通过 |
| 云/团队/认证/账单 | 有明确协作需求、维护能力和独立授权；不塞进本地 1.0 |
| 多数据库/微服务/大规模性能优化 | 受支持工作负载的实测瓶颈，SQLite/单服务简单方案已不足 |
| 全平台 runtime、自动更新器 | 当前支持平台稳定且新增平台有用户与测试资源 |
| 全站改版、移动端、多语言 | 当前主要任务的可用性证据说明必要；不是因为觉得“不像成品” |

新增需求进入停车场时只记录：谁遇到、证据、阻碍哪一步、最小可能方案。没有这四项，不排期。

## 15. 阶段决策权与下次开工指示

助手负责：在已授权切片内选择最小实现、验证、展示结果、记录风险；主动拒绝无证据扩张；每个里程碑提供继续/收窄/暂停建议。

用户保留：目标用户/定位的大变化、付费 API 与预算、外部联系与数据共享、支持平台承诺、迁移性破坏、远端发布及任何重要范围扩大。

普通实现细节不重复请示。发现“只有重写后端才做得了”等方向性变化时先提供证据和备选，不自己扩大授权。

执行入口始终以 CURRENT_TASK 的下一片为准，依次完成验收、自检、DEVLOG、CURRENT_TASK 和 ROADMAP 进度更新后交付。无需重做接管审计、B1/B2 或 PyPI 准备。规划本身不改版本号，不开新发布，不把未来 agent 能力写成当前 README 事实。

最终判断标准：**1.0 是一个边界明确、别人愿意反复用来完成真实工作的工具，不是一个把所有热门 AI 概念装进去的版本号。**
